# Release gate: the unverified marks against the real Agents

Issue: [#80](https://github.com/samfaina/config-digger/issues/80). Terms follow [`CONTEXT.md`](../../CONTEXT.md).

Before v0.1 ships, every Unverified mark of the built-in definitions is tested against the real Agent on the reference machine (Windows 11 Pro, home `C:\Users\kgon1`, a second drive `E:`). Each mark is then removed, or the rule is corrected, with the evidence in the definition as a `[test]` tag and here. This file covers the three CLI Agents, tested on 2026-10-23; the marks that need Windows Sandbox, since their files sit in `%ProgramFiles%` or `%ProgramData%`, or come with an installer; Claude Code's marks that need a claude.ai account, tested on 2026-10-24 with the owner's Max account; Claude Code's marks about plugin bundles, plugin skills and server values of the wrong shape, tested on 2026-10-28; VS Code's marks about the MCP files it reads, and about its stores, its account's policy and its skills, tested on 2026-10-24 on throwaway profiles, the policy with the owner's GitHub account; Cursor's marks about the MCP files and plugins it reads, tested on 2026-10-24 on throwaway profiles, the plugins of a Project's settings with the owner's Cursor account; and Cursor's marks about its Disabled store, its skills and its feature gates, tested on 2026-10-25 on throwaway profiles, its window driven, with the facts of its nested skills folders (#134) the same day. Cursor's marks about a plugin manifest whose servers have the wrong shape and the order of two nested skills were tested on 2026-10-28 the same way, as were VS Code's marks about its built-in and updated extensions. It also covers how Orca copies the Codex home, tested on 2026-10-24 by running Orca 1.4.239's own code on throwaway homes. Claude Desktop's skills mirror was tested on 2026-10-29 in Windows Sandbox, signed in to the owner's account. Claude Code's marks about what takes it off its claude.ai account, and its synced plugins, were tested on 2026-10-30 with the owner's Max account, and its marks about the case of the Project's state and the managed settings' approvals the same day, the latter in Windows Sandbox, as were its marks about a synced plugin, and a plugin off or forced off, whose manifest fails (#459), the forced-off plugin in Windows Sandbox. The rest of Claude Desktop, which needs its window driven, comes next.

## The probes

A probe per Agent in `uat/agents/` builds throwaway homes and Projects, runs the real Agent on them and checks what it loads:

```powershell
node uat/agents/claude-code.mjs [--bin <claude.exe>]
node uat/agents/codex.mjs       [--bin <codex.exe or codex.cmd>]
node uat/agents/gemini-cli.mjs  [--bin <gemini.cmd>]
node uat/agents/vscode.mjs      [--bin <Code.exe>]
node uat/agents/cursor.mjs      [--bin <Cursor.exe>]
node uat/agents/orca-codex.mjs  [--orca <Orca's install folder>]
```

Each check names the table of the definition it tests, as `cargo xtask unverified` prints it, and passes when the Agent does what the definition now says. A probe exits 1 when a check fails. `CD_PROBE_VERBOSE=1` prints what each check saw, and `CD_PROBE_JSON=<file>` writes the results. Run a probe again with each new version of its Agent: when every check passes, the version can join the definition's `verified` range.

What keeps a probe off the user's own configuration:

- Everything sits under `CD_PROBE_ROOT`, `E:\cd-throwaway-agents` by default, whose name must start with `cd-throwaway`. It is outside the user's home folder on purpose: Claude Code reads `CLAUDE.md` and `.mcp.json` in every folder above the one it starts in, so a Project under `C:\Users\<me>` would pick up the user's own files.
- Each Agent gets a throwaway home: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or `GEMINI_CLI_HOME` in the temp folder. Gemini CLI's home is on the system drive and its Projects on `E:`, so that a rule for the home folder and one for a Project sit on different drives. The Claude Code launch that tests the home folder's `.mcp.json` also moves `USERPROFILE` and `HOME` to a throwaway folder, and the one that tests the root of a drive starts on a drive `subst` maps to a throwaway folder, which the probe takes off again.
- Servers are `cmd /c <tag>`, which exits at once, or an HTTP URL on a closed local port. Entries are `cd-throwaway-*` and the only key is `not-a-real-secret`.
- No request reaches a model. Claude Code's Messages API is a local server in the probe, which keeps each request so the probe can read the skills Claude Code lists to its model. Codex and Gemini CLI point at a closed local port.
- Claude Code still fetches its GrowthBook features at start, without an account. Older Claude Code versions come from npm into the probe root (`npm install --prefix E:\cd-throwaway-agents\cc-<version> @anthropic-ai/claude-code@<version>`).
- VS Code gets a throwaway profile per launch: `--user-data-dir`, `--extensions-dir`, `--shared-data-dir` and `--agent-plugins-dir`, and `USERPROFILE` and `APPDATA` in the launch's folder, so that `~\.vscode\argv.json` and Claude Desktop's config are throwaway too. It runs beside a VS Code the user has open, and the probe stops only the processes given its own data folder. Its servers are this machine's Node writing a marker file, or answering as an MCP server with one tool. The launch that reads VS Code's cache of ExP assignments sets the telemetry level to `all`, without which VS Code ignores the cache, and points VS Code's requests at a closed local port, `--proxy-server` and `http.proxy`, so that neither the telemetry nor a request for assignments is meant to leave the machine. Another version comes as the zip archive from `update.code.visualstudio.com/<version>/win32-x64-archive/stable`, unpacked into the probe root. The launch of built-in extensions passes `--builtin-extensions-dir`, a copy of the Installation's `resources\app\extensions` with the probe's added, so the Installation stays as it is, and installs the other extensions from VSIX files with VS Code's own CLI, `cli.js` run by `Code.exe` as `bin\code.cmd` runs it.
- Cursor gets a throwaway profile per launch too: `--user-data-dir` and `--extensions-dir`, and `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` in the launch's folder, so that `~\.cursor` and `~\.claude` are throwaway. The probe stops only the processes given its own data folder. Its servers are this machine's Node writing a marker file. The sign-in checks run a local MCP server behind OAuth, which grants `not-a-real-secret` and answers its own authorization request by calling Cursor's loopback redirect. `workbench.externalBrowser` hands every URL Cursor opens to `curl.exe`: Cursor opens its own sign-in page at first start, and a browser started with the launch's `LOCALAPPDATA` would make a new profile there. Signed out, Cursor takes each feature gate's default from its code, unless the profile's `workbench.experiments.featureFlagOverrides` overrides it, which Cursor reads only while it runs an extension under development: the launches that turn gates off write those overrides and load an empty extension with `--extensionDevelopmentPath`. The `skills` launch's home folder is `<drive>:\Users\cd-throwaway` on a drive `subst` maps to a folder of the launch, and the probe takes the drive off once Cursor stops.
- Orca's copy of the Codex home is tested without the Orca that is open, which copies from the `~\.codex` of the user it runs as, whatever `CODEX_HOME` says, and writes settings back into it. `orca-codex.mjs` loads the main-process modules an Orca install unpacks, `resources\app.asar.unpacked\out\main\chunks\codex-home-paths-*.js` and `managed-agent-hook-controls-*.js`, in Node, with `USERPROFILE` and `ORCA_USER_DATA_PATH` in throwaway folders, and runs what Orca runs before it starts a Codex on its home. The exports' names are those of Orca 1.4.239's bundler: the probe stops when the paths they give are not the throwaway ones. A second Orca on throwaway folders was not tried: it starts a Codex on this home only for a launch whose `CODEX_HOME` is not `~\.codex`, which would have to be driven in its window.
- Only the `plugins[project]` checks run signed in to a Cursor account, the owner's, on the throwaway profile `E:\cd-throwaway-agents\cursor-account`: without an account, Cursor resolves no plugin key of a Project's `.cursor\settings.json`. `node uat/agents/cursor.mjs --sign-in` opens that profile for the owner to sign in, with only `USERPROFILE` moved, so that the sign-in page opens in the owner's own browser.
- Only the `policy` check of `vscode.mjs` runs signed in to a GitHub account, the owner's, on the throwaway profile `E:\cd-throwaway-agents\vscode-account`: VS Code caches an account's policy only once signed in. `node uat/agents/vscode.mjs --sign-in` opens that profile with only `USERPROFILE` moved, and waits while the owner signs in from the Accounts menu and closes the window; nothing is driven. VS Code 1.129.1 to 1.141.0 keep the GitHub session in the shared data folder's store on Windows, so the probe's launches on that profile keep its `--shared-data-dir`.

### In Windows Sandbox

Three probes write what only an administrator or an installer writes: `claude-code-machine.mjs` (`%ProgramFiles%\ClaudeCode`, `HKLM` and `HKCU\SOFTWARE\Policies\ClaudeCode`), `codex-machine.mjs` (`%ProgramData%\OpenAI\Codex\requirements.toml`) and `claude-desktop.mjs` (the classic installer and the MSIX package claude.ai serves). Each refuses to run outside Windows Sandbox, whose only user is `WDAGUtilityAccount`, so nothing reaches the reference machine. `uat/agents/sandbox.ps1` runs them there:

```powershell
.\uat\agents\sandbox.ps1                                  # the three probes
.\uat\agents\sandbox.ps1 -Probes claude-code-machine -Claude <claude.exe>, <claude.exe>
.\uat\agents\sandbox.ps1 -Probes claude-desktop -KeepOpen # leaves the Sandbox open
.\uat\agents\sandbox.ps1 -Probes claude-desktop -SignedIn -KeepOpen
```

It maps into the Sandbox, read-only, the probes, this machine's Node (Volta's image, not its shim), a copy of each Claude Code binary `-Claude` names (`~\.local\share\claude\versions\<version>` included), Codex's `codex.exe` from its npm package, and the Claude Desktop installers, which it downloads from `claude.ai/api/desktop/win32/x64/{exe,msix}/latest/redirect`. The Sandbox's logon command, `in-sandbox.ps1`, runs each probe with `CD_PROBE_VERBOSE`, `claude-code-machine.mjs` once per Claude Code binary, writes `<probe>.log` and `<probe>.json` to `%TEMP%\cd-agents-sandbox\results`, and shuts the Sandbox down. With `-KeepOpen` it stays open and runs the probes again whenever `results\rerun.txt` appears, from the copies in `%TEMP%\cd-agents-sandbox\probes`, which a rerun may copy over. `-SignedIn` runs `claude-desktop.mjs --signed-in`: it installs the package alone, starts it, and its log says `SIGN IN` while it waits, up to 20 minutes, for the owner to sign in from the Sandbox's window, with the email code rather than Google. It goes on once the app has written the account's skills mirror, and a later run in the same Sandbox finds the app signed in.

| Probe | Oracle |
|---|---|
| `claude-code-machine.mjs` | `claude mcp list` (servers, approval status, parse diagnostics) and whether `claude -p` answers the local model stand-in; for a plugin the managed settings force off, `claude plugin list` and the `init` event of `claude -p --output-format stream-json --verbose` |
| `codex-machine.mjs` | `codex mcp list`: `enabled`, or `disabled: requirements (<file>)` |
| `claude-desktop.mjs` | The files the installers write, and the servers the app starts: each `claude_desktop_config.json` declares a server whose command writes a marker file named after its folder. Signed in: the skills mirror, `skills-plugin\<org>\<account>`, its `manifest.json` and its `SKILL.md` files, after a sync round the app's log reports as `[SkillsPlugin] Sync complete` |

### With a claude.ai account

`claude-account.mjs` tests the skills and plugins Claude Code syncs from claude.ai, its sync gates, and what takes it off the account. It needs a home signed in to claude.ai, and the owner signs in to a throwaway one once, outside their own home folder:

```bash
CLAUDE_CONFIG_DIR='E:\cd-throwaway-agents\claude-account-home' claude auth login --claudeai
node uat/agents/claude-account.mjs [--bin <claude.exe>]
CLAUDE_CONFIG_DIR='E:\cd-throwaway-agents\claude-account-home' claude auth logout
```

`!` in a Claude Code prompt runs bash, so `$env:CLAUDE_CONFIG_DIR=…` there signs in the user's own home instead. `CD_PROBE_ACCOUNT_HOME` names another signed-in home, a folder named `claude-account-home*` in the probe root; the probe refuses any other, and runs only when `claude auth status` says `claude.ai` and no variable that takes Claude Code off the account or its gates is set. Its model is the local stand-in, so no prompt reaches a model; Claude Code still signs in, fetches its gates and downloads the account's skills. It plants skills beside the synced ones, sets the gates' cached values in `.claude.json`, and puts them back at the end. Its oracle is the `init` event's skills, the skill listing and the body of a skill a `/<name>` prompt runs, as for `claude-code.mjs`, and what Claude Code downloads into `skills/synced/<organizationUuid>_<accountUuid>`.

The account checks add the `init` event's plugins and `claude auth status --json`, whose `authMethod` and `apiProvider` say which auth Claude Code picks. They plant a synced plugin with `syncedPlugin()` of `lib.mjs`, which also lists it in the account's `manifest.json`, as Claude Code loads no other, and one in another account's folder. Claude Code reads synced plugins only while their gate is on, and each run's sync round deletes a plugin claude.ai does not list, so these sessions run with `HTTPS_PROXY` at a closed port and the model stand-in left out by `NO_PROXY`: the gates keep their cached values and no round runs. Each check sets one thing: `apiKeyHelper`, `env.ANTHROPIC_AUTH_TOKEN`, `env.CLAUDE_CODE_OAUTH_TOKEN` or `env.CLAUDE_CODE_USE_BEDROCK` in the user's or the Project's settings, `primaryApiKey` or `customApiKeyResponses` in `.claude.json`, or a variable in one session's environment, and puts the file back after. Bedrock points at a closed port, and the session is stopped after its `init` event. Signed out is tested on copies of the signed-in home, one without `oauthAccount` and one without `.credentials.json`, which the probe deletes at the end; `claude auth logout` never runs on a copy, which shares the home's tokens. A second synced plugin, with a skill, a server in its `.mcp.json` and one in its manifest, has its manifest rewritten between sessions; `claude plugin list --json` gives the error of a synced plugin that fails to load under the `id` `synced[<n>]`, so the check finds it by its `installPath`, and the folder outlives every offline session. The check takes the plugin out once it has seen it.

## The marks

The inventory is the 80 marks of `main` at `5cb2ad5` (`cargo xtask unverified`): 20 in Claude Code, 15 in Codex, 4 in Gemini CLI, 4 in Claude Desktop, 17 in Cursor and 20 in VS Code. The skill manager definitions hold none. Line numbers are those of `5cb2ad5`.

Outcomes:

- **Confirmed**: the Agent does what the mark assumed. The mark is gone and the fact carries `[test]`.
- **Corrected**: the Agent does something else, and the definition now says what. The mark is gone.
- **Ticket**: the Agent does something else that the definition format or the core cannot express yet. The mark is gone, the definition states the fact with `[test]` and names the ticket.
- **Pending**: not tested yet. The mark stays, and the reason says what the test needs.
- **Pending, under the exception**: #80's last criterion lets a mark stay untested when its test needs an account or a deployment the project does not have: a Codex enterprise account, Claude Teams or Enterprise, a Claude Desktop deployment for a third-party provider, or a Cursor team account. The release notes list such a mark with what its test needs.

## Found beside the marks

- **Claude Code names a skill by its folder**, on every version tested from 2.1.286 to 2.1.309, against its docs and the definition, which named it by its frontmatter. The frontmatter `name`, when the name rule lets it, is an alias: `/fold-a` and `/<name>` both run the skill. `skillOverrides` turns a skill off by its folder, so Disable wrote a key Claude Code never read for a skill whose `name` differs from its folder. One consequence: a skill folder Claude Code and VS Code both read is now one name in both, which `show` cannot pick between ([#301](https://github.com/samfaina/config-digger/issues/301)).
