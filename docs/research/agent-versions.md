# Research: how v0.1 Agents expose their version and feature gates

Issue: [#32](https://github.com/samfaina/config-digger/issues/32). Feeds [#37](https://github.com/samfaina/config-digger/issues/37) ("Unknown Agent versions and feature gates"). Terms follow [`CONTEXT.md`](../../CONTEXT.md).

Checked on Windows 11 Pro 10.0.26200, home `C:\Users\kgon1`, on 2026-10-02, against: Claude Code 2.1.287 (native), Claude Desktop 2.16120.0.0 (MSIX `Claude_pzs8sxrjxfjjc`, developer-signed; see §1.3 for why this is probably not the Store build), VS Code 1.129.1 user setup with the built-in GitHub Copilot Chat 0.57.0, Cursor 3.22.12 user setup, Codex CLI 0.159.3 and Gemini CLI 0.62.0 (both `npm i -g` under Volta). No GUI app was started. SQLite databases were copied to a scratch folder and read there. Each fact is tagged:

- **[disk]**: verified read-only on this machine (files, registry, AppX, file version resources, the apps' own shipped code).
- **[test]**: observed by running a CLI's `--version` with its home folders pointed at an empty scratch folder (see §1.2).
- **[source]** / **[docs]**: stated by the Agent's source code or official docs, not observed here.
- **unverified**: could not be confirmed.

Secret values and account or org UUIDs are never reproduced.

## Summary

- **Every v0.1 Agent's version can be read from a file without starting it.** The cheap and reliable sources are the Windows file version resource of the Electron/native executables (Claude Code, Claude Desktop, VS Code, Cursor), the MSIX package identity (Claude Desktop), `resources\app\package.json` / `product.json` (VS Code, Cursor) and the npm package's `package.json` (Codex, Gemini CLI, npm Claude Code). Inno Setup uninstall keys give the same value for VS Code and Cursor.
- **A version belongs to an installation, not to an Agent home.** Several installations can read one Agent home (three Claude Code binaries share `~/.claude` here, including the one Claude Desktop downloads), and one installation can read several Agent homes (`CODEX_HOME`, VS Code profiles). Most Agents also record **the version that last ran against a given home**: `lastReleaseNotesSeen` in `~/.claude.json`, `client_version` in Codex's `models_cache.json`, `releaseNotes/lastVersion` in VS Code's and Cursor's `state.vscdb`. That is the better answer to "which version reads this Agent home", but it is stale until the Agent next runs.
- **`--version` is not side-effect free everywhere.** `claude --version` wrote nothing [test]. `codex --version` tries to create helper binaries under `CODEX_HOME\tmp\arg0` before printing [test]. `gemini --version` creates `~/.gemini` and leaves `projects.json.<uuid>.tmp` files behind [test]. config-digger should never need to run a CLI: the files carry the same value.
- **Every Agent has some server-side control over config behaviour. Four cache it on disk in readable form, Codex only sometimes, Gemini CLI never:**
  - Claude Code: GrowthBook features in `~/.claude.json` → `cachedGrowthBookFeatures` (plain JSON, gate names in clear text, 801 entries here). Several touch MCP servers, claude.ai connectors and skill/plugin sync.
  - Claude Desktop: GrowthBook features in `<userData>\fcache` (8-byte magic + gzip of JSON, 24-hour expiry, 391 features here). Keys are opaque numeric ids, so the meaning of each must be recovered from the app bundle per release.
  - Cursor: the Statsig bootstrap in global `state.vscdb` → `workbench.experiments.statsigBootstrap`, gate names hashed with **djb2**, which is not a secret hash. Hashing the names found in Cursor's code resolves the three gates the Cursor research could not read: `dedupe_mcp_servers`, `mcp_profile_scoped_global_disabled_state` and `enable_cc_plugin_import` are all **on** here.
  - VS Code: Microsoft's ExP/TAS assignments in `state.vscdb` → `memento/experiment.service.memento`, which can change the default of `onExp` settings. Separately, the GitHub account's Copilot policy can turn MCP off or restrict it to a registry through the `chat.mcp.access` policy, cached under `defaultAccount.cachedPolicyData`.
  - Codex: no experiment system. Its feature flags are local `[features]` keys, and the only server channel is the enterprise cloud config bundle, cached for one hour in `%CODEX_HOME%\cloud-config-bundle-cache.json` (absent here).
  - Gemini CLI: Code Assist experiments decide whether admin controls apply, and those can switch MCP servers, extensions and skills off or allowlist servers. Both are kept **in memory only**; only the auth type in `settings.json` tells whether they can apply.
- **Claude Desktop correction.** The installed `Claude_pzs8sxrjxfjjc` package is developer-signed, and Anthropic's Intune README says the Store build is `AnthropicPBC.Claude`. `research/claude-desktop` had the two package families the wrong way round (§1.3).
- **Every cached gate value is per account and goes stale.** It reflects the last time the Agent ran and fetched, for whichever account was signed in. config-digger can show it as "as of <time>", never as current truth.

### 1.2 Running `--version`

Each CLI was run once with `USERPROFILE`/`HOME` (and `CLAUDE_CONFIG_DIR` or `CODEX_HOME`) pointed at empty scratch folders, from an empty working folder, and the scratch tree was listed afterwards. The real homes' files kept their timestamps.

| Command | Output | Side effects in the redirected home | Tag |
|---|---|---|---|
| `claude.exe --version` | `2.1.287 (Claude Code)` | none | [test] |
| `codex.exe --version` (native binary, not the npm shim) | `codex-cli 0.159.3`, preceded by `WARNING: proceeding, even though we could not create PATH aliases: Refusing to create helper binaries under temporary dir ...` | It **tries to create helper binaries under `CODEX_HOME`** before printing; it refused only because the scratch home was under `%TEMP%`. With a normal home it writes there | [test] |
| `node bundle\gemini.js --version` | `0.62.0` | Created `~/.gemini\` and left two empty `projects.json.<uuid>.tmp` files | [test] |

Why, from source:

- **Codex.** `main()` runs `arg0_dispatch_or_else` before clap parses arguments. It loads `CODEX_HOME\.env`, creates `CODEX_HOME` and `CODEX_HOME\tmp\arg0`, deletes unlocked `codex-arg0*` folders and creates a new `codex-arg0XXXXXX\` with `apply_patch.bat`/`applypatch.bat`, then prepends it to `PATH`. Release builds refuse to do this under `%TEMP%`, hence the warning ([cli/src/main.rs L1013–L1033](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/cli/src/main.rs#L1013-L1033); [arg0/src/lib.rs L60–L421, L494–L536](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/arg0/src/lib.rs#L343-L421)) [source]. `~/.codex\tmp\arg0` holds four leftover `codex-arg0*` folders here [disk]. The version clap prints is the compile-time `CARGO_PKG_VERSION`; the workspace version is committed in `Cargo.toml` ([L160–L161](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/Cargo.toml#L160-L161)) [source]. No `VERSIONINFO`/winres exists in the repo, which matches the empty version resource [source] [disk].
- **Gemini CLI.** `--version` is handled by yargs only after the parent process has re-spawned itself as a child and the child has run `loadSettings()` (which reads all settings files, checks folder trust, reads `.env`, can **rewrite** a settings file to migrate deprecated keys, and fails on a broken settings file), read and deleted `%TEMP%\gemini-cli-warnings.txt`, and fired an un-awaited `Storage.initialize()` that creates `~/.gemini` and writes `projects.json` ([packages/cli/index.ts L54–L116](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/cli/index.ts#L54-L116); [gemini.tsx L466–L540](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/cli/src/gemini.tsx#L466-L540); [settings.ts L919–L991](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/cli/src/config/settings.ts#L919-L991); [core/src/config/storage.ts L277–L324](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/core/src/config/storage.ts#L277-L324)) [source]. The docs say it will "Show CLI version number and exit" ([docs/cli/cli-reference.md](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/docs/cli/cli-reference.md)) [contradicts docs in spirit]. The bundled version is a build-time constant from `package.json` ([esbuild.config.js L97–L100](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/esbuild.config.js#L97-L100)) [source], so `package.json` is equivalent. Gemini CLI keeps no update-check cache file; the update check queries npm live ([packages/cli/src/ui/utils/updateCheck.ts L56–L133](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/cli/src/ui/utils/updateCheck.ts#L56-L133)) [source].
- **Codex update cache.** `version.json` is written by the TUI's background update check (at most every 20 hours) and holds the latest *available* version, from GitHub releases or npm ([tui/src/updates.rs L27–L132](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/tui/src/updates.rs#L27-L132)) [source]. `models_cache.json` `client_version` is the compile-time version of the binary that last fetched the model list ([models-manager/src/lib.rs L19–L26](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/models-manager/src/lib.rs#L19-L26)) [source].

VS Code and Cursor were not run. Their `bin\code.cmd` / `bin\cursor.cmd` launch the GUI executable with `ELECTRON_RUN_AS_NODE=1` and `out\cli.js` [disk]; the files in §1.1 give the same answer without that.

### 1.3 Install variants from primary sources

**Claude Code** ([setup](https://code.claude.com/docs/en/setup), [troubleshoot-install](https://code.claude.com/docs/en/troubleshoot-install)) [docs]:

- Native installer: `%USERPROFILE%\.local\bin\claude.exe`, versions under `%USERPROFILE%\.local\share\claude`. It keeps the launcher's target, any running version and the two newest versions. Native installs auto-update.
- WinGet `Anthropic.ClaudeCode`: a `portable` package that downloads `claude.exe` ([winget manifest](https://github.com/microsoft/winget-pkgs/tree/master/manifests/a/Anthropic/ClaudeCode)). WinGet portable apps go to `%LOCALAPPDATA%\Microsoft\WinGet\Packages\<id>_<source>\` with a link in `%LOCALAPPDATA%\Microsoft\WinGet\Links\` and an Apps & Features entry ([winget portable spec](https://github.com/microsoft/winget-cli/blob/master/doc/specs/%23182%20-%20Support%20for%20installation%20of%20portable%20standalone%20apps.md)); the exact folder suffix is **unverified**. WinGet installs do not auto-update unless `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1`.
- npm `@anthropic-ai/claude-code`, which pulls the native binary through `@anthropic-ai/claude-code-win32-x64`/`-arm64`; a legacy `%USERPROFILE%\.claude\local` npm install also exists.
- The docs show `claude --version` printing `<ver> (Claude Code)` but say nothing about side effects; `claude doctor` is documented as read-only. A setting literally named `autoUpdates` is no longer in the settings reference, although `~/.claude.json` still carries `autoUpdates: false` here [disk]; the documented switches are `autoUpdatesChannel`, `minimumVersion`, managed `requiredMinimumVersion`/`requiredMaximumVersion`, `DISABLE_AUTOUPDATER` and `DISABLE_UPDATES` ([env-vars](https://code.claude.com/docs/en/env-vars)).
- Claude Desktop keeps its own Claude Code at `%APPDATA%\Claude\claude-code\<version>\claude.exe` ([3P installation](https://claude.com/docs/third-party/claude-desktop/installation.md)) [docs]; for an MSIX install that path is virtualised to the package's `LocalCache\Roaming\Claude` [disk].

**Claude Desktop** [docs]:

- Windows ships as an `.msix` and a legacy `.exe`; only the MSIX gets Cowork ([3P installation](https://claude.com/docs/third-party/claude-desktop/installation.md), [Windows checklist](https://claude.com/docs/government/deploy-desktop/windows-checklist.md)).
- Anthropic's Intune README names the MSIX `Claude`, family `Claude_pzs8sxrjxfjjc`, publisher "Anthropic, PBC", and says **the Microsoft Store build has a different identity, `AnthropicPBC.Claude`** ([Intune README](https://downloads.claude.ai/releases/enterprise/intune/Claude-Intune-README.md)). The installed package here reports `SignatureKind: Developer` [disk]; Store-delivered packages report `Store` ([`PackageSignatureKind`](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.packagesignaturekind)). So this machine has the directly downloaded MSIX, and `research/claude-desktop` had the two families the wrong way round: `Claude_pzs8sxrjxfjjc` is the direct/enterprise MSIX and `AnthropicPBC.Claude_fnn82j28hfe8t` the Store build. **[contradicts prior research]** For version detection it does not matter: both are read the same way.
- **A user who is not an administrator cannot list `C:\Program Files\WindowsApps`**: `read_dir` fails with `PermissionDenied` (os error 5), while the folder of an installed package, such as `Claude_4.29.0.0_x64__pzs8sxrjxfjjc`, and its `app\claude.exe` can be read once its path is known [test, 2026-10-29, #469]. So a folder glob below `WindowsApps` finds nothing. An Installation names its package family instead, `folder = { block = "msix-package", family = "Claude_pzs8sxrjxfjjc" }`: config-digger asks Windows for the family's packages installed for the current user, `GetPackagesByPackageFamily`, and for each one's folder, `GetPackagePathByFullName`, neither of which needs elevation ([`GetPackagesByPackageFamily`](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagesbypackagefamily), [`GetPackagePathByFullName`](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagepathbyfullname)) [docs]. A family can hold several packages, such as a resource package beside the main one: only a folder that holds the executable is an Installation. The family names the publisher id, so a `Claude` package of another publisher is not Claude Desktop.
- winget `Anthropic.Claude` 1.44121.2 lists both an `msix` and an `exe` installer; the exe has scope user and `ProductCode: AnthropicClaude` ([winget manifest](https://github.com/microsoft/winget-pkgs/tree/master/manifests/a/Anthropic/Claude)). Squirrel installs to `%LocalAppData%\<App>\app-<version>\` and writes `HKCU\...\Uninstall\<appName>` with `DisplayVersion` and `InstallLocation` ([Squirrel install process](https://github.com/Squirrel/Squirrel.Windows/blob/develop/docs/using/install-process.md)). Hence the inferred classic paths in §1.1, **unverified**.
- Releases roll out gradually and auto-update is on by default; policy keys `disableAutoUpdates` and `autoUpdaterEnforcementHours` control it ([3P installation](https://claude.com/docs/third-party/claude-desktop/installation.md)).

**VS Code** [source] [docs]:

- User setup installs to `{userpf}` with `PrivilegesRequired=lowest`, system setup to `{pf}`; user and system installs can coexist with only a warning ([`build/win32/code.iss`](https://github.com/microsoft/vscode/blob/main/build/win32/code.iss), [setup docs](https://code.visualstudio.com/docs/setup/windows)).
- Uninstall keys are `Software\Microsoft\Windows\CurrentVersion\Uninstall\{AppId}_is1`, AppId per target and arch from the distro `product.json` ([`gulpfile.vscode.win32.ts`](https://github.com/microsoft/vscode/blob/main/build/gulpfile.vscode.win32.ts)). Microsoft's GUIDs are not in the OSS repo; the stable user x64 one is confirmed here [disk], the others come from secondary sources ([GitHub Desktop's editor detection](https://github.com/desktop/desktop/blob/development/app/src/lib/editors/win32.ts), [vcpkg-tool](https://github.com/microsoft/vcpkg-tool/blob/main/src/vcpkg/commands.edit.cpp)): stable user x64 `{771FD6B0-FA20-440A-A002-3B3BAC16DC50}`, arm64 `{D9E514E7-1A56-452D-9337-2990C0DC4310}`; stable system x64 `{EA457B21-F73E-494C-ACAB-524FDE069978}`, arm64 `{A5270FC5-65AD-483E-AC30-2C276B63D0AC}`; Insiders user x64 `{217B4C08-948D-4276-BFBB-BEE930AE5A2C}`, system x64 `{1287CAD5-7C8D-410D-88B9-0D1EE4A83FF2}`. Enumerating uninstall keys by `DisplayName` avoids depending on the GUIDs.
- The build writes `version`, `commit` and `date` into `product.json` (not only `package.json`), and the installer adds `"target": "user"|"system"`; non-stable builds get a quality suffix such as `-insider` ([`gulpfile.vscode.ts`](https://github.com/microsoft/vscode/blob/main/build/gulpfile.vscode.ts)). `target: user` is present here [disk]. A `product.json` without `target` means a ZIP build, the only one where portable mode (a `data` folder next to `Code.exe`) applies ([`bootstrap-node.ts`](https://github.com/microsoft/vscode/blob/main/src/bootstrap-node.ts), [portable docs](https://code.visualstudio.com/docs/editor/portable)).
- The `<commit10>\resources\app` layout (`win32VersionedUpdate`) arrived in [PR #263998](https://github.com/microsoft/vscode/pull/263998) and was enabled for stable in [PR #288126](https://github.com/microsoft/vscode/pull/288126) (January 2026; first stable version **unverified**, probably 1.109). **Several commit folders can coexist during an update**: the new folder is installed next to the old one with `new_Code.exe` and an `updating_version` file, and `inno_updater --gc` removes old folders later; for user setup only on the next start ([`code.iss`](https://github.com/microsoft/vscode/blob/main/build/win32/code.iss), [`updateService.win32.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/platform/update/electron-main/updateService.win32.ts)). ## 2. Feature gates and experiments per Agent

### 2.2 Claude Desktop

- **Mechanism.** GrowthBook, fetched from `/api/desktop/features` every 60 minutes (`main.log`: `[growthbook] loaded 391 features (0 changed)`, `next refresh in 60 min`) [disk, bundle].

## 3. Implications for config-digger

1. **Read versions from files, never by running the Agent.** Per Agent, one primitive suffices: file version resource (Claude Code, Claude Desktop, VS Code, Cursor), AppX package query (Claude Desktop MSIX), JSON field in a manifest (VS Code/Cursor `product.json`, npm `package.json`, Codex `codex-package.json`), registry uninstall key (fallback and for discovering installs). `--version` is unsafe for Codex and Gemini CLI.
2. **Report versions per installation and map installations to Agent homes.** The "last version that ran against this home" fields (`lastReleaseNotesSeen`, `models_cache.json` `client_version`, `releaseNotes/lastVersion`) connect the two. Where installations disagree (three Claude Code binaries here, or a VS Code update in flight), the definition's `verified` range has to be checked against each, or against the last-run one.
3. **Gate values are readable for Claude Code, Cursor, VS Code and (when cached) Codex; not for Gemini CLI.** A feature-gate entry in an Agent definition could name a lookup (file, key path, hashing) and an assumed default, and the reason sentence can say "assumed on; last seen on as of <time>" or "cannot be read". The Claude Desktop ids are too unstable to put in a definition.
4. **Cursor's three open gates are settled for this machine**: all on. The Agent definition can treat the gated variants as the current behaviour, and keep the ungated variant only as a fallback when the cache says off.
5. **Auto-update makes any cached version stale between scans** (Cursor, Claude Desktop, native Claude Code). Versions should be read at every scan.
